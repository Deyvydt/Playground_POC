  Importante: un "agente" aquí no es un programa distinto. Es una fila en la
  base de datos (tabla Agent) con: un prompt de rol (sus instrucciones), un
  modelo de Ollama, una temperatura, y una lista de herramientas permitidas. Al
  arrancar el backend, seed.py inserta estos 6 registros en SQLite si no existen
  todavía (backend/app/main.py:17 llama run_seed()).

  2. Cómo se orquestan (el motor es uno solo)

  Todo pasa por una única función: run_agent_turn en
  backend/app/orchestrator.py:11-121. No hay 6 motores distintos, hay 1 motor
  genérico que recibe "cuál agente" como parámetro y ejecuta siempre el mismo
  flujo:

  1. RAG: busca fragmentos relevantes en la base de conocimiento del agente
     (rag.retrieve, línea 45).
  2. Prompt: arma el mensaje de sistema = role_prompt del agente + contexto
     recuperado (si hay).
  3. Llamada al LLM: ollama_client.chat(...) (línea 71).
  4. Tool-calling opcional: si el modelo pide usar una herramienta (ej.
     calculadora), se ejecuta en tools.py y se le devuelve el resultado al
     modelo; esto se repite hasta 3 veces (MAX_TOOL_ROUNDS = 3, línea 8).
  5. Traza: cada paso (retrieval, prompt, llamada al modelo, tool-call,
     respuesta final) se guarda en una lista trace que se devuelve completa —
     así se cumple el principio de "observabilidad" del proyecto.

  Esta misma función la reutilizan dos flujos distintos:
  - Chat 1-a-1 (backend/app/routers/chat.py:74): usuario habla con un solo
    agente, con historial de conversación.
  - Orquestación multi-agente (backend/app/routers/orchestration.py:51-58): es
    un pipeline secuencial. Se le da una lista de IDs de agentes, y la salida de
    cada agente se convierte en la entrada del siguiente (_next_input, línea
    15-20). No es un grafo complejo ni paralelo — es una cadena simple A → B →
    C.

  3. Cómo consumen los LLMs de Ollama

  Hay un solo punto de contacto con Ollama en todo el backend:
  backend/app/ollama_client.py. Nadie más le habla a Ollama directamente (está
  prohibido por el AGENTS.md del repo, principio de "independencia de
  proveedores").

  - chat() (línea 31) → POST /api/chat en http://localhost:11434 — genera la
    respuesta y maneja tool-calling nativo de Ollama.
  - embed() (línea 52) → POST /api/embeddings — genera los vectores para el RAG.
  - Si Ollama falla o no responde, lanza ModelUnavailableError, que los routers
    capturan y convierten en un HTTP 503 con mensaje claro.

  Es básicamente un adaptador/gateway: todo el resto del sistema solo conoce
  funciones como "chatear" o "generar embedding", nunca URLs ni formato HTTP de
  Ollama.

  4. Qué arquitectura es (y cómo notarlo tú mismo)

  Es una arquitectura en capas (layered), tipo monolito simple — no es hexagonal
  ni microservicios. Así se ve:

  routers/*.py        → capa API (delgada, solo valida y delega)
  orchestrator.py,
  rag.py, tools.py     → capa de lógica de negocio
  ollama_client.py    → capa de infraestructura (adaptador externo a Ollama)
  models.py + SQLite  → capa de datos

  Cómo darte cuenta tú mismo, sin que nadie te lo diga:

  - No es microservicios porque solo hay un proceso (uvicorn app.main:app, un
    solo puerto 8000) y una sola base de datos (playground.db, SQLite, un
    archivo). Microservicios significa varios servicios independientes, cada uno
    desplegable por separado, normalmente con su propia base de datos y
    comunicándose por red/colas. Aquí no existe nada de eso — todo corre en el
    mismo proceso.
  - No es hexagonal "puro" porque no hay interfaces/puertos abstractos (no hay
    un AgentRepository o LLMPort como clase abstracta que luego se "inyecta").
    La lógica de negocio (orchestrator.py) importa y usa directamente Session de
    SQLModel y el módulo ollama_client — es decir, depende directamente de la
    infraestructura, no de una abstracción. En hexagonal real, el dominio no
    sabría ni que existe SQLite u Ollama.
  - Sí es por capas, porque hay una separación clara de responsabilidades: los
    routers/ son delgados (solo HTTP), la lógica vive en archivos de "servicio"
    (orchestrator, rag, tools), y el acceso a Ollama está aislado en un solo
    archivo (ollama_client.py). Esto es justo lo que dice el propio AGENTS.md
    del repo como regla de diseño.
  - El frontend es una SPA separada (React + Vite) que solo consume la API REST
    (frontend/src/api/client.js), sin estado propio de servidor — es front/back
    desacoplados, pero sigue siendo "monolito backend + SPA", no microservicios.

  Pista rápida para el futuro: si quieres confirmar la arquitectura de cualquier
  repo, mira (1) cuántos procesos/servicios se despliegan por separado, (2) si
  la lógica de negocio depende de clases abstractas o directamente de librerías
  externas, y (3) cuántas bases de datos hay. Un proceso + una DB + dependencias
  directas = monolito en capas, como este caso.

  Para responder tu pregunta directamente: no, no hay "nodos" ni grafo de 
  agentes. Lo que existe es mucho más simple:

  - No hay grafo: LangGraph modela agentes como nodos de un grafo con aristas
    condicionales (el flujo puede ramificarse, repetirse, decidir dinámicamente
    a dónde ir). Aquí no hay nada de eso.
  - Lo que hay es una lista + un bucle for: en orchestration.py:51, el
    "pipeline" es literalmente:
  for agent in _load_pipeline(session, payload.pipeline):
      result = await run_agent_turn(session, agent, [], running_input,
  user_id=user.id)
      steps.append(_step(agent, result))
      running_input = _next_input(payload.input_text, agent, result["content"])
  Es una cadena lineal A→B→C armada a mano: el texto de salida de un agente se
  concatena como texto de entrada del siguiente. No hay enrutamiento
  condicional, no hay estado compartido tipo grafo, no hay un "supervisor" que
  decida el siguiente nodo — el orden lo define quien llama al endpoint (manda
  la lista de IDs en el orden que quiere).
  - Tool-calling tampoco usa ningún framework: es Ollama nativo (/api/chat con
    el campo tools) + un if tool_calls: manual en orchestrator.py:92-107 que
    ejecuta la función en tools.py y vuelve a llamar al modelo. Eso es lo que
    LangChain llamaría un "agente ReAct", pero aquí está hecho sin
    abstracciones, en ~15 líneas de Python puro.
  - Multi-agente = reutilizar la misma función varias veces, no varios agentes
    "corriendo" simultáneamente ni comunicándose entre sí directamente.
    run_agent_turn no sabe nada de orquestación: solo sabe ejecutar un turno de
    un agente. Quien encadena es orchestration.py.

  En resumen: es un pipeline secuencial hecho a mano, sin ningún framework de
  agentes de por medio. Si quisieras algo tipo LangGraph (ramificaciones,
  memoria compartida entre agentes, loops condicionales, un supervisor que
  decide), habría que construirlo — hoy no existe esa capa.
